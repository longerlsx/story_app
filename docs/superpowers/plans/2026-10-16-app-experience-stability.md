# 应用全面排查与体验优化计划（最终修订版）

日期：2026-10-16。状态：实施中。用户已批准以下计划并授权分步提交、推送。完整参考基线提交：`6142bc3`；其 APK 身份及前序验证见[当前状态](../../current-state.md)。规则源为[协作约定](../../knowledge/agent-operating-agreements.md)。

## 1. 目标、基线与执行原则

全面覆盖启动、书架、导入、阅读、听书、设置及退出恢复，优先保证**正文完整、声音可靠、操作可控、位置准确**，再优化有实际影响的等待、卡顿和资源消耗。

- 主类型为体验与稳定性修复，次类型为性能优化。允许根据重要新发现调整顺序和扩大必要改动，不预设大规模重构或大幅性能收益。
- 保持四线程、三步、完整参考、免费离线及现有单一音色为听书基线；音质和内容完整性优先。
- 本轮以 `StoryReader_API34` 模拟器完成验收，真机后补。手机温耗、厂商后台行为及扬声器／耳机体验保持独立验证边界。
- 原始 TXT、书籍身份、用户设置、阅读及听书位置必须保留。分页修正可以改变页数，不能丢失、重复正文或破坏定位。
- 默认不新增产品功能、不改变外部入口及存储格式，不迁移数据库、不替换引擎。内部接口和结构按确认的问题作必要调整。
- 遵循项目 docs 的证据、验证准入、委派和交付规则。一次性验收代码预算预计接近 0 行、硬上限 800 行，默认不进入仓库；优先扩展已有长期测试。

本文件持续记录重要发现、取舍、验证摘要及剩余问题。

## 2. 执行顺序与重点

### 阶段一：固定基线，先走一次完整流程

先检查工作区，将已完成的“三步＋完整参考”改动及相关文档独立提交、推送，保留同签名基线 APK 和身份信息。

集中修复前，用基线包正常操作一次：

**开书 → 阅读与调整设置 → 开始听书 → 浏览／换章 → 后台 → 返回 → 退出恢复。**

- 使用现有真实小说，覆盖一个章节边界和一次操作尚未完成时的新输入。
- 记录显示、起读位置、控制响应、声音、明显等待和恢复位置；动态过程保留短录屏及实际音轨。
- 这一步只做代表流程，不重跑全套历史测试。录音工具先用已知发声和一次明确暂停校准，避免采集故障污染判断。
- 根据发现重新排序。正文／位置错误、数据风险、崩溃和错误播放优先；截字始终保持高优先级。
- 若多个问题涉及共同状态或布局逻辑，先确定共同原因，再安排修复，减少重复改动。

### 阶段二：阅读显示、章节与目录

**截字调查与修复**

- 按用户描述检查末行字形下半部分消失，直接核对真实页面、文字布局和容器边界。
- 分别验证已有的宽度取整差异、段距累计取整差异；若排除，继续检查父容器约束、字形绘制边界和布局切换。
- 扩展现有页面完整性测试，覆盖临界断行、多短段、跨页长段、不同字号及分数像素条件。预期结果必须来自实际渲染，不能复制分页计算作为答案。
- 原因确认后统一必要的测量与显示约束，不用额外空行、缩小正文区域或强制换行掩盖问题。
- 同步验证正文顺序、章尾、续段缩进及重排后的文字位置。

**章节识别与旧目录**

- 为 `第2 章` 等明确格式缺口补失败用例，再作窄修复；保留正文误切、标点及标题长度防线。
- 复用 9 本真实小说测试，提取缺失、额外、重复和顺序差异，核对差异上下文后固定正确预期。候选正则和粗略标题数量不能作为完整性答案。
- 区分新解析错误与旧书保留历史目录。取得旧目录时，与同一原文的新解析结果只读比较。
- 不预先增加重新分章入口，也不自动重切旧书。只有确认旧目录造成实际问题且新结果更正确，才启动第 4 节的迁移分支。

### 阶段三：听书与读听交接

- 检查冷启动准备中暂停／停止、重新开始、播放中改速、通知打断、主动暂停、后台控制及定时停止。
- 串联当前页起读、播放中浏览、切模式、目录换章、继续或重开、通知返回，核对声音、画面、控件、定时和保存位置。
- 保留当前语义：新开从显示正文起读，暂停继续沿用原会话，停止后旧任务不复活。主动暂停后重读未完成短句，不直接认定为异常重复。
- 复用当前引擎和播放日志；只有现有记录无法对应具体片段时，增加最少的段标识及开始／结束时间记录，不建立新监控框架。
- 不重复短参考、两步、三线程等已撤回路线。发现重复生成、无效等待或过时任务占用后，再进行应用层优化。

### 阶段四：补齐其他流程，进行有依据的性能优化

覆盖连续前后翻页、目录覆盖旧导航、调整排版后立即退出、长章滚动与反向恢复、换书、导入失败、重复导入、坏书隔离、面板与返回、日夜主题、窄屏大字和横屏。

性能观察包括开书、跳目录、重排、长章滚动、首次发声、继续播放及连续使用的资源变化：

- 区分首次准备、缓存命中、过时工作和实际显示／播放耗时。
- 优先消除已确认的重复工作、无效等待和资源未释放。
- 性能改动采用同设备、同输入、同类 release 构建，至少三组成对交替比较，以用户等待和可见停顿为主要指标。
- 收益无法与基线波动区分，或损害内容、音质、响应及内存表现时撤回。
- 本轮不承诺提速、降温或节电百分比。

## 3. 验证标准，尤其是听书验收

生产行为修复先取得失败证据，再实施和验证。复用现有测试，历史证据按原版本和条件继承。

### 听书验收的共同执行约束

**以下听书验收必须从正式应用入口开始，经过生产使用的分段、预取、会话调度和播放流程；直接调用引擎仅用于诊断，不能替代体验验收。**

至少覆盖一次冷启动后的**“短首段 → 长第二段”**：

- 确认旧进程已结束，从正常应用入口重新启动，不事先手动预热模型或预生成音频。
- 选择由正式分段规则自然产生短首段、较长第二段的正文，记录实际分段和原文偏移；不手工构造语音段绕过生产规则。
- 连续记录点击、首声、第二段生成与实际播放，检查首声等待及两段之间的衔接。不能等第二段准备完成后才开始观察。
- 该场景纳入下面的短样本和连续性检查，不另建测试框架。

### 听书分三项独立验收

**A. 短样本内容与音质**

- 固定四类代表文本：长短句衔接、对话、多段数字／专名、分段及章节边界；每类约 150–300 字，记录原文位置。
- 以 1×和常用 1.45×取得实际播放录音，逐段核听清晰度、失真、漏读、截尾和异常重复。
- 转写辅助对齐原文和定位可疑片段，不能单独证明没有失真；专名同音识别差异必须回听判断。
- 发现异常即记录，额外复测用于归因，不选取最好的一次掩盖失败。
- 通过条件：固定样本中没有尚未解释或处理的明显声音缺陷。无法完成可靠听辨时，音质保持待验，不能以有声、波形或转写通过代替。

**B. 连续播放流畅性**

- 使用保留真实时间间隔的实际播放录音，对齐原文分段、生成日志及播放事件。不能用拼接后的合成音频或会省略空闲时间的模拟器 WAV 后端统计停顿。
- 校准并固定低电平检测参数，对完整录音扫描；所有不少于 0.6 秒的内部低电平区间逐项归因。该值沿用项目既有调查口径，是调查触发线。
- 区分合成音频自带的正常停顿、明确操作／焦点中断、采集故障与供给／调度造成的等待。
- 通过条件：没有未解释的告警，没有确认由供给或调度造成的不少于 0.6 秒意外空档；更短但反复造成可感知卡顿的情况也必须处理。
- 录音缺失或时间轴失真时，该窗口无效，修正采集后补验，不能据播放状态或进度增长通过。

**C. 持续运行与定时**

- 最终候选完成一次至少 15 分钟真实引擎播放，包含自然跨章、熄屏片段和定时停止。
- 保留完整音轨并按 B 项分析；核听首、中、尾片段、章节边界及全部异常区间。
- 同时检查进度推进、通知状态、定时结束和资源释放。
- 现有“音频不活跃接近 30 秒、进度接近两分钟不推进”的检查仅保留为卡死保护，不能作为流畅性标准。15 分钟运行通过也不能代替 A 项音质检查。

### 其他核心验收

| 范围 | 通过标准 |
|---|---|
| 页面 | 原文顺序与章尾完整，实际末行字形不被裁切，续段正确 |
| 连续操作 | 最终目标符合有效输入，过时请求不覆盖新状态，过程中不闪回旧章或旧视口 |
| 导入与章节 | 已确认标题及特殊边界正确，切片准确，失败不损坏原书，重复导入不重复建书 |
| 读听控制 | 声音与目标文字一致，停止后不复播，暂停与焦点恢复遵守用户意图 |
| 恢复 | 确认位置和设置保留；实际进程结束再启动后不擅自播放，不以 Activity 重建代替 |
| 升级 | 基线产生数据后覆盖候选，原文、书籍、设置及读听位置兼容 |

最终执行一次全量 JVM 单测、受影响设备回归、必要构建和静态检查。同一最终相关代码已有有效结果时直接继承，不因提交或文档整理重复运行。

## 4. 新问题纳入与旧数据迁移的条件

### 新问题处理规则

每项发现记录症状、证据、影响、优先级、最小方案和直接验收方法：

- 正文／位置／数据错误、崩溃和错误播放立即优先。
- 可复现的常用操作障碍、明显等待和卡顿纳入本轮。
- 静态疑点先作最小取证；有充分防护依据或实验排除后关闭。
- 多个重要问题具有共同根因时，允许集中调整相关模块。
- 两个假设连续被否定后重新检查前提，避免叠加猜测性补丁。
- 无体验影响的整理、没有收益证据的微优化不扩大范围。常规实现选择自主处理；改变既定产品约束或不可逆数据处理需重新对齐。

### 仅在确需旧目录迁移时启用

- 使用同一正规化原文，将旧章内位置换算为绝对字符位置，再映射阅读和听书进度；保留书籍身份、原文、设置及最近使用信息。
- 迁移在相关读写停止时进行，具备可恢复提交和重复执行保护；验证任一步骤中断后只能恢复一致的旧状态或新状态。
- 固定回退目标为迁移前最后已验收提交及对应同签名 APK。
- **优先保持存储格式兼容，让回退版本直接正确读取迁移后的目录和进度。** 若不能直接兼容，必须提供对应版本的数据恢复办法，并在交付迁移前验证。
- 必测：**旧版本产生数据 → 新版本迁移 → 继续读听并产生新进度 → 回退版本重新打开**，核对目录、正文、阅读位置和听书位置。
- 仅恢复迁移前备份不算充分回退，必须处理迁移后新增进度。无法保证时，不交付自动迁移。
- 未实施迁移时，本节不增加测试和实现工作。

## 5. 提交、推送、文档与收尾

已授权分步提交和推送，执行时不再逐项询问。

- 默认沿用 `feat-android-reader-foundation` 及对应远端；检查远端变化，正常同步，不强推或改写已发布历史。
- 先独立提交前序完整参考恢复，再提交本轮计划；后续按一个问题或紧密相关改动形成中文提交。
- 每步依次完成：修复、直接回归、受影响流程验证、必要文档更新、差异检查、提交与推送。
- 已推送代码使用独立 revert 提交回退；涉及数据迁移时同时执行已验证的数据兼容或恢复安排。
- 当前行为维护在 `docs/current-state.md`，确认缺陷更新对应 bug 记录和索引，执行证据摘要维护在本轮计划。
- 调查可并行委派，共享构建和设备操作串行；复杂改动进行独立检查，不建立重复审查链。
- 最终交付同签名 ARM64 APK，附提交身份、SHA256、改善内容、验证范围及剩余限制；保留回退基线，清理一次性诊断产物。

结项要求：代表流程有有效证据，已确认的重要缺陷关闭，没有未解释的测试失败或重要退化。偶发报告未复现时明确列出覆盖条件和剩余缺口，不标为已修复，也不宣称全部问题已解决。达到约定范围后停止扩查；真机后补项目单独保留。
