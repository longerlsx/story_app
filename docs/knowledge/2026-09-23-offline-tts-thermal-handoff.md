## 已经查清的成本边界

基线热态20秒simpleperf（99Hz、task-clock:u、DWARF）有7729样本、0丢失，约98.7%用户态CPU样本在`libonnxruntime.so`，因此本轮优先推理而非UI。相同二进制的已识别地址中，UMMLA计算子集622样本（8.05%），yield／原子读取等待子集246样本（3.18%）；**只是指令子集，不是全部计算／空转比例，等待也未必可消除**。

单独的真机ORT profiling取得三个有效JSON：14次Encoder共0.315秒、56次Decoder共43.643秒、14次Vocos ONNX共2.080秒。Decoder占合计46.037秒的94.8%，这是**已记录model_run墙钟占比，不是CPU、能耗或可节省比例**。14次App生成均对应1 Encoder＋4 Decoder＋1 Vocos；未覆盖带实际文字短尾的双块情况。末次Run在停止标记后约2.04秒完成，未见持续新生成，也没有证据说取消后仍播放或推进进度。

该profile含探针开销，未覆盖初始化、参考前处理、Run外更新与原生IStft；节点`thread_scheduling_stats`没有逐工作线程CPU／自旋／睡眠时间，`num_run`包含跨节点累计活动，不能把主线程Wait当浪费。固定sherpa 1.13.8已有`cpu:配置文件`及`ProfilingFilePrefix`入口，不必为启用profiling重编原生库；当时三个会话分别正常落盘，探针随后移除。若以后需要，先读现存JSON／摘要，不把带探针包拿去做正式温耗对照。

[官方 `speaker_info_dict` 缓存](https://github.com/k2-fsa/ZipVoice/blob/master/runtime/nvidia_triton/pytriton_server.py#L78-L97)保存参考tokens、Mel特征和RMS，避免参考读取／前处理；仍调用模型生成和vocoder，不缓存完整Encoder结果或Decoder迭代。App已缓存参考WAV，而参考前处理在上述ORT计时之外。缓存或共享线程池可能有机会，但现有证据没有把它列为主要可回收成本，不应重新当作已确认高收益方案。

## 后续若重新开工，优先回答什么

1. **先看所选组合的实际使用反馈。** 三步短参考的长正文清晰度、专名／数字、节奏和连续播放仍未知；若出现问题，记录具体文本、发生处与所用APK，优先用已测三步完整D作对照。不要回到被用户否决的两步，除非用户重新选择。
2. **若仍要证明温耗收益，再约一个明确窗口。** 原门槛是同机同文1.45×亮屏不充电20分钟，末5分钟skin均值较45.853°C至少低1.5°C、电池终点较42.7°C至少低1°C、电荷损失≤387.6mAh，并再取得同方向有效重复。初温、SOC、室温及录音开销都要记录；本轮用户曾允许按实际初温继续，不能据此抹去差异。阶段结项没有把这些未完成门槛改判通过。
3. **先解决电荷读数解释，再报节电比例。** D最后两分钟读数不更新，停止后才补跳；结束瞬间的单点值会偏乐观，追加空闲尾部又不等窗口。需核实可用读数、记录更新时间和停播后变化，不能减去猜测的空闲耗电。电池服务温度、实时HAL电池／skin、系统热状态和用户手感分别报告。
4. **只有新证据再改调度或分段。** 首段实际发声后才串行准备后两段。短首段→长第二段必须满足“第二段生成＋调度时间小于首段自然音频时长÷语速”，现有两段预备不代表启动时已有库存。加长段还扩大手动暂停后的重读、进度粒度和改速生效等待；临时焦点中断则保留PCM位置。旧native取消尾部约2秒不能直接作为长块的新上限。

连续性必须看实际声音并对齐生成／AudioTrack日志：silencedetect检测的是低电平，不能将所有静音称供给缺口；源偏移有序也不证明逐字无漏读。已有冷／热各35秒转写未发现整句漏读／重复，只覆盖那些四步基线片段。D的无长静音、三步短参考桌面试听不能替代任意正文正确性、整夜熄屏、热态2×或17 Pro验证。
